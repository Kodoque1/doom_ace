Doom inside Doom inside Doom inside the first Doom

Doomception

Three Doom games in one DOOM2.EXE. Each one shows the next on a wall.

By @KODOQUE · built on kgsws' ACE Engine, which loads new code into DOS Doom 2. Doomception wouldn't exist without it.

Why it's cool

Four reasons

  1. No operating system. DOS has no processes or threads. It's all done by hand, inside the game.
  2. The nesting is visible. Each game's wall shows the next game, and the picture loops.
  3. A few instructions to pause one game and resume another.
  4. A program written to run alone is made to share. Only what differs is swapped: about 1,300 bytes per switch out of 577 KB.

The model

How it works

  • One DOOM2.EXE: its code and data are shared by every copy.
  • Each copy, a depth, has its own memory: heap, stack, screen buffer, ACE code.
  • One CPU runs one depth at a time.
  • Every 4 frames a switch swaps in the next depth's data, patches and pointers, then hands it the CPU.
  • Each depth draws the next one on a wall.

ACE: ACE Engine by kgsws, a Doom 2 mod shipped as a WAD that loads new engine code into the game. Doomception adds the switch to it.

Up close

Anatomy

Three small pictures of the real mechanism: what a depth is, what a switch does, and how the pictures loop.

A depth

A depth is its own memory, plus a saved copy of everything it shares with the other depths.

  • Data. Doom's data is one live copy. Most of it is the same in every depth; the few bytes that differ (coloured) are the running depth's.
  • Pointers. Three globals in the shared data, mainzone, ACE's screen_buffer and Doom's screens[0], point at the running depth's heap and screen.
  • Patches. ACE patched 406 places in Doom's memory, most of them in its code. They call the running depth's ACE code; the other depths' patch bytes wait in their snapshots.
  • Host state. Which depth runs, and every suspended depth's stack pointer, sit in one block that no snapshot covers.

In the code: nested/dos_wire.c (mtx_dos_wire_register).

A switch

Every 4 frames the host saves one depth, loads the next, re-points the pointers and swaps the stacks.

In the code: nested/mtx_core.c (mtx_switch), nested/dos_state.c (mtx_dos_save_state, mtx_dos_load_state), nested/mtx_sched.c (mtx_frame_tick).

The pictures

Each depth draws into its own screen buffer. One wall texture reads the next depth's buffer. The monitor shows one buffer.

  • Every frame the host tells each depth whose buffer its wall shows (screen_src). The deepest depth wraps to depth 0.
  • A suspended depth doesn't draw, so its wall picture is that depth's latest frame.

In the code: engine/mtx_boot.c (mtx_ring_next, mtx_world_screen, mtx_engine_video).

    Your turn

    The challenge

    Write the switch yourself. A tiny computer, a TinyDoom and a C compiler, all in one kit: make three copies share one machine.

    1. Take turns.
    2. Keep their data apart.
    3. Keep their patches apart.
    4. Keep their pointers apart.
    5. Survive a hostile level.
    6. Close the ring.

    A checker proves each step, then scores you on cycles and bytes.

    ▶ Play it in your browser

    Edit your scheduler, check it, and watch the machine run it, one instruction at a time if you like. Everything on that page is the kit's own C compiled to WebAssembly, so its verdicts are the same as make check in sandbox/, which also runs locally.
