Three copies of a game engine run inside one DOS process, and none of them was written to share it. This article explains how the matryoshka host makes them take turns, what each copy has to own, and the seven times something turned out to belong to the wrong owner.

Map 01

A program that believes it is alone

The goal: N live instances of the ACE engine coexisting inside one running DOOM2.EXE, switched at runtime, without ever re-launching the executable.

ACE is a replacement engine for Doom 2 version 1.9. It ships inside a WAD file and takes over a stock, unmodified DOOM2.EXE through two quirks of the original engine (a negative-size lump allocation and a read past the stack). That bootstrap is a finished, frozen piece of work, and this article treats it as a black box. Once ACE is resident, nesting becomes a different problem entirely, and that problem is the subject here.

Start with what a single copy of the engine assumes about the world. None of these assumptions is a bug. Each one is reasonable for a program that expects to be the only one running.

  1. Its globals live at fixed addresses. Doom's mutable data is 416 variables spread over 475,676 bytes. A second copy running the same code uses the same addresses.
  2. Its main loop never returns. D_DoomLoop has no exit. You cannot call it and wait for it to finish.
  3. There is no C runtime. ACE has no libc: no threads, no setjmp, no memcpy unless you write the loop yourself.
  4. It rewrites code. ACE installs 405 patches into Doom's memory, and 399 of them land in Doom's code segment.
  5. It owns the machine. It owns the screen at 0xA0000, the keyboard interrupt, and a heap that takes all the remaining RAM.

Now imagine the naive plan: jump into the engine's entry point a second time. The stock first-stage loader works out its own base address from the startup stack (sub $0x34615,%esi), and that arithmetic is only true once. The stock second stage frees the lump cache, the lump table and the heap, closes every WAD file, and then jumps into the engine, which destroys the parent's world before the child starts. The child's Z_Init asks for all the free RAM, and none is left. Its renderer draws into the parent's screen. Its ace_main re-patches Doom code that the parent is executing.

Every one of those failures gets a section below. They all have the same shape, though, and it is worth stating that shape before the details.

An instance is its state. If you can name every byte that a program can change, you can run several copies of it on one machine. You swap those bytes at a moment when nothing is in flight. The engineering lies in the naming. Every serious bug in this project turned out to be a byte whose owner had been named wrong.

Map 02

Taking turns without threads

The first problem is control flow. Depth 0 is somewhere deep inside Doom's frame loop. We want to stop it, run depth 1 for a while, and later continue depth 0 at the exact instruction where it stopped. DOS has no threads to do this for us.

Look at what a suspended C function actually needs in order to continue. It needs its stack, which holds return addresses, locals and arguments. It also needs the registers that C promises to preserve across a call: ebx, esi, edi and ebp. It does not need eax, ecx or edx, because the function that calls the switch already expects those to be destroyed. So a "thread" is really just a stack pointer. Give each depth its own stack, and switching depths means swapping ESP.

Here is the whole primitive, the only part of the scheduler that had to be written in assembly:

mtx_switch_ctx:                 /* (uint32_t **save_esp, uint32_t *load_esp) */
	mov	4(%esp), %eax		/* eax = save_esp */
	mov	8(%esp), %edx		/* edx = load_esp (new ESP value) */
	push	%ebp
	push	%ebx
	push	%esi
	push	%edi
	mov	%esp, (%eax)		/* *save_esp = esp */
	mov	%edx, %esp		/* switch stacks */
	pop	%edi
	pop	%esi
	pop	%ebx
	pop	%ebp
	ret				/* resumes the loaded depth */

The switch is symmetric. The depth that switches away later resumes right after its own call to mtx_switch_ctx, as if it had made an ordinary function call that took a long time. That leaves one puzzle: a depth that has never run has nothing to resume. Step through it below.

The trick for a fresh depth is a forged suspension. mtx_seed() writes the stack a switched-out depth would have: four zeroed register slots, then the address of mtx_trampoline where a return address would sit, then the entry argument. The first switch into it "restores" the zeros and its ret lands in the trampoline, which calls the depth's entry function. Nothing is special-cased. A new depth looks to the switch exactly like an old one.

This is also why the code doesn't use setjmp/longjmp. Those need a C runtime, and they assume the jump target's frame is still alive. Here the frames that have to stay alive belong to a game loop that never returns.

Read the animation once with one question in mind: what does a depth "remember" while it is frozen? Nothing beyond its stack, and the stack pointer that leads back into it. When control comes back, every function on that stack simply returns, one after another, as if nothing had happened.

Map 03

A safe place to stop

A cooperative switch only happens when the running code calls it, and the running code is Doom's frame loop. So where should the call go? Switch in the middle of rendering and you leave a half-drawn frame and a renderer whose state is mid-update. Switch in the middle of game logic and you suspend a world partway through a tic.

The answer is the frame boundary: after a frame is rendered and before it is presented. At that moment the engine has no work in flight. Anyone can request a switch at any time (an input handler, a timer, the scheduler), and the request only becomes an actual switch the next time the engine reaches that point:

void MTX_FRAME_TICK_ABI mtx_frame_tick(void)
{
	uint8_t k = sched_kind;

	if(k == MTX_REQ_NONE)
		return;

	/* Consume BEFORE switching: neither the incoming depth nor this one when it
	   is resumed later may re-service the same request. */
	sched_kind = MTX_REQ_NONE;

	if(k == MTX_REQ_YIELD)
		mtx_yield();
	else if(k == MTX_REQ_SWITCH)
		mtx_switch_to(sched_depth);
}

Notice the line that clears the request before switching. The switch doesn't return until someone switches back, possibly many frames later, and by then the request must already be gone. Otherwise the resumed depth would service it a second time. Try both orders below.

Deep dive: finding a hook that actually runs

The obvious frame boundary is swap_buffers() in engine/vesa.c, ACE's replacement for Doom's I_FinishUpdate. In the first live boot it never ran, because it is only hooked when VESA activates, and VESA did not activate on DOSBox's emulated S3 card for a 320×200 mode. hook_draw_stbar only runs during levels, while the title screen is a different game state. ACE's assembly I_FinishUpdate runs in every state, but calling C from there crashed the game (Illegal read … CS:IP 170:b02c7d5c, black screen), because it is entered from a Doom path where the C calling convention does not hold.

The request/consume pair is what made a game-state-dependent hook acceptable: a pending request simply waits for the next frame that reaches the yield point. Today the frame path runs from swap_buffers() through mtx_engine_frame().

Deep dive: the calling-convention promise

swap_buffers is declared __attribute((regparm(2),no_caller_saved_registers)), which means it promises its Doom callers that eax, ecx and edx survive the call. A plain C function called from inside it is allowed to clobber all three, and that would silently break the promise. So mtx_frame_tick carries the same attribute, and gcc saves those registers around the switch. The attribute also forces -mgeneral-regs-only, because such a function may not touch x87 state.

Map 04

What an instance is made of

Control flow is solved. Two depths now run on two stacks, but they still share every global variable, and a global that one depth writes is a global the other depth reads. The real work of nesting is the inventory: which bytes belong to a depth, and what has to happen to them on a switch.

The answer comes in four kinds, plus a fifth that belongs to no depth at all. Try sorting them yourself before reading on. Pick a card, then pick the bin you think it belongs in.

The first four kinds are registered by a wiring layer (dos_wire.c), so the save/load code itself knows nothing about Doom. The fifth gets its own section, Map 05. A depth's snapshot is seeded by cloning the parent's live state the first time the depth is entered. A child starts as a copy of its parent and then diverges, which is what a nested instance should do.

The patches nobody snapshots

Regions cover data, and Doom's code segment is not data. ACE does not patch its own code. It patches Doom's: calls redirected into ACE, constants changed, instructions overwritten with NOPs. A second instance's ace_main re-patches that shared code while the root is executing it. Without a fix, a patch made by any depth is visible to every depth.

The host builds its list by reading the engine's own hook table (_hooks_start…_hooks_end) at boot. It never transcribes addresses by hand, because a hand-written list would rot the first time the engine gained a hook, and the resulting failure would look like random memory corruption instead of a missing entry. Why pins exist

Some globals are pointers to memory that must not be shared. mainzone points at the heap. If it came back from the snapshot unchanged, a child cloned from its parent would allocate from the parent's heap. So after the snapshot is restored, the host forces these pointers to the incoming depth's own values.

There are three pins, not two, and the third one was found by testing where pixels landed. ACE copies Doom's screens[0] into its own screen_buffer exactly once, at init. After that the two are separate variables, and Doom's renderer keeps drawing through its copy. With only ACE's pointer pinned, a nested depth still painted over the root's frame. The test writes a marker through Doom's pointer at depth 1 and then searches both buffers for it:

Map 05

The host was standing inside the guest

With all that in place the host booted inside DOOM2.EXE, depth 1 came up, and everything looked healthy until the first real switch. That switch produced 2,000 illegal reads and writes, plus DYNX86: Can't run code in this page. The baseline build has zero.

Here is the question that had been skipped: where does the scheduler keep its own variables? mtx_ctx[], mtx_cur and the inited[] flags were ordinary globals, so they lived in the engine's .bss. That is the same .bss the snapshot saves and restores on every switch. The switch was restoring its own bookkeeping while it was still using it.

Reproduce it below. The order of operations inside mtx_switch() is fixed: save the outgoing depth, write cur, load the incoming depth, then swap stacks.

Whose bytes are these?

Step-through

The fix is a rule about ownership: all host control state lives in one object, mtx_hs, and the wiring layer registers the engine's .bss as two regions, one below that object and one above it. The split is exact because mtx_hs is a single object, so the linker can place other data before or after it but never inside it. If that ever stops holding, the host refuses to nest at all. The boot log confirms the split: the snapshot dropped from 536,262 to 529,468 bytes per depth, which is exactly sizeof(mtx_hs).

The same bug, a second time

The next crash was exception 06h (invalid opcode) at a garbage EIP. The useful clue was that ESP still pointed into the root's stack, which meant the bad jump happened before the stack swap, so the resumed depth could not be at fault. That left the calls the switch makes before swapping, which go through the save/load function table. mtx_init() had kept a pointer to that table, and the engine had passed it the address of a local variable in a boot function whose stack frame was long dead by the first switch.

Now mtx_init() copies the table into mtx_hs. The first regression test for this also hid the bug: it compared the kept pointer against the dead frame's address, but returning a dead local's address is undefined behavior, so gcc folded it to NULL and the test passed against the buggy code. The test that works today inspects the table the scheduler will actually call. It calls mtx_init from a helper whose frame is then overwritten with 0x4D4D4D4D, and asserts that the callbacks still work.

Map 06

Booting a second engine

So far, depth 1 has been a purpose-built test guest, a few dozen bytes of position-independent code loaded from a WAD lump. A real nested instance is the whole ACE engine image: about 400 KB, which relocates itself, clears its own .bss, builds a heap, initializes video and patches Doom. Each of those steps had been written for a program that runs once.

A loader that cannot do harm

The stock second-stage loader is one-shot by construction: it frees the parent's memory and closes the parent's files before jumping into the engine. The reentrant version, ldr1n.c, fixes that structurally. Its entire authority is a table of three services:

typedef struct {
    int32_t  (*read)(void *ctx, int32_t fd, void *dst, uint32_t n);
    void    *(*alloc)(void *ctx, uint32_t n);
    void     (*enter)(void *ctx, void *code, uint32_t code_base,
                      uint32_t data_base, uint32_t ace_base);
} mtx_ldr1n_ops_t;

There is no free() and no close(). The loader cannot destroy the parent's state because it has no way to. That is a stronger guarantee than a comment saying "don't free anything here", because it is enforced by what the loader can call. The first stage, ldr0N.S, takes its base addresses as data instead of deriving them from the startup stack, and assembles to 39 bytes, well inside the 256-byte patch budget of the original.

The original first stage never returned, so it was free to use EBP as scratch. The reentrant copy kept that habit, which meant it destroyed its caller's frame pointer, and nothing that intends to continue can call such a function. It now saves and restores EBP, which costs two instructions and still fits in 39 bytes.

It also loaded the hand-off registers before calling Doom's printf to print its banner. printf is a C function, so it clobbers ecx, and the next stage received a garbage argument. In the live run the guest ignored that register, so the bug corrupted a value nobody was reading. A DOS run can't catch that kind of bug. Host test [11] does: it points code_base at a stand-in printf (ldr0N reaches it at code_base + 0x3FE40) and records exactly which registers arrive.

Telling an instance what it is

A nested instance is a relocated copy of the engine with its own .bss. Its mtx_hs is therefore a different, empty object. In the first attempt, the instance's allocator consulted that empty object, decided it was the root, and asked DPMI for 209,184 bytes when only 61,440 were free. Meanwhile its own memory pool sat unused.

The host now fills a parameter block for each depth inside its own mtx_hs and hands the block's address over in %ebp at the entry. A register is used because the entry clears .bss, which would erase anything the host wrote into the instance beforehand, and EBP is the one register the entry doesn't consume. The engine validates the block by its contents: the magic word 'MTXP' plus the block's own address stored inside it. When a root boots, EBP holds whatever the loader left there, the check fails, and a null block is exactly the signal that this copy is the host.

The obvious place to store the pointer was the assembly entry, using the same mov %eax,mtx_params(%ecx) idiom the rest of the entry uses. The assembler records that displacement as a relocation, so the entry's own relocator added the image base to it a second time and the store landed elsewhere. The pointer stayed null through an entire nested boot. The store now happens in C, where it is an ordinary relocated absolute reference.

A heap of its own, checked with Doom's own rules

Doom's allocator walks a ring of block headers, so handing a depth raw memory is not enough. The first Z_Malloc would read an uninitialized header. Each depth's heap is built inside its arena slot and checked against the same invariants Doom's Z_CheckHeap enforces.

build 0 means the checks passed. alloc 3987516 is Doom's real Z_Malloc returning a pointer inside the depth's heap: 3987516 − 3987460 = 56, which is 32 bytes of zone header plus 24 bytes of block header. probe 0 means the invariants still hold after an allocate-and-free round trip.

A clue spelled in ASCII

The instance booted, drew frames, and then died on some runs with errors that made no sense as Doom errors: Lump PLAYFAL read failed!, W_CacheLumpNum: 19796 >= numlumps, and a 1.5 GB allocation request. The pattern becomes clear once you decode the numbers. The host stamps memory with magic words, and magic words are readable text. Try it:

Decode the log

Tool

A lump index of 0x4D54 is "MT", the top half of 'MTXR', which is the header magic of the depth's raw memory pool. So Doom was reading pool metadata as data. The pool's own arithmetic turned out to be the problem, in three ways that are each easy to get wrong:

  • The tip test compared the requested size instead of the space a block occupies. A 1-byte request occupies 8 bytes, so such a block was never recognized as the newest one. The engine's lump table starts as a 1-byte allocation and is grown to tens of kilobytes. Each grow moved the block and leaked the original, and the lump table quietly stopped growing.
  • The pool trusted its base address to be aligned. The arena comes from Doom's allocator, which is happy to return 4-byte alignment. The pool landed 4 bytes off, its ownership check rejected all of its own memory, and frees fell through to the DPMI heap, which handed back pointers untouched.
  • A zero-byte request needs real space. Refusing it turned a working call into Texture memory allocation failed! (0B). Serving it with no payload put the caller's first byte in the next block's header.

The pool also counts every leak and every refused request. That makes "the pool is big enough" a number you can check rather than an assumption.

Map 07

One screen, many worlds

Three instances now render three frames, but the monitor can show only one. Every frame reaches VGA memory through a single assembly routine, ACE's I_FinishUpdate, which copies 64,000 bytes to 0xA0000. The copy's source address isn't a variable. It is baked into the routine's own code at init:

1141:  57                   push %edi
1142:  56                   push %esi
1143:  51                   push %ecx
1144:  be 78 56 34 12       mov $0x12345678,%esi   <- the source, patched at +4

1153:  f3 a5                rep movsl %ds:(%esi),%es:(%edi)

Every depth originally presented the root's buffer, so a nested instance's frames could never reach the screen. Now the host owns that immediate, and each depth has its own copy of the routine, so the host tells each depth's blit what to copy from (present_src).

Setting a pointer is not evidence that the screen changed, so the host reads the screen back. It compares the first dword of VGA memory with the chosen buffer, one frame later, because the blit for the current frame hasn't run yet when the policy decides:

Screens inside the world

Showing one instance at a time proves the plumbing but makes for a dull picture. The finished version is diegetic: one wall surface in each level is a TV, and it shows another instance's frame. Which instance is decided by the ring rule:

static uint8_t mtx_ring_next(uint8_t d)
{
	uint8_t k;

	for(k = 1; k < MTX_MAX_DEPTH; k++)
	{
		uint8_t c = (uint8_t)((d + k) % MTX_MAX_DEPTH);

		if(mtx_alive(c))
			return c;
	}
	return d;                       /* nothing else live: nothing to show */
}

The modulo is the wrap. Without it, the deepest level's TV would have nothing to show and the chain would be a ladder. With it, the levels close into a cycle and every picture contains the whole nest. Each step inward is one lap older, because the frame on a TV is whatever that instance drew the last time it ran. The console below runs the same rule, and lets you take the wrap away.

Painting happens in two phases. During Doom's wall loop the engine only records, for each screen column, where that column falls on the TV. After the frame is finished, it fills those columns from the other instance's framebuffer. The first version drew directly inside the wall loop, where Doom's clipping state is mid-calculation, and produced 112 writes outside video memory and a black screen. The picture is placed in wall space, so perspective and occlusion are Doom's own. It is drawn without Doom's distance darkening, because a screen gives off light, and a darkened screen looks like a texture rather than a picture.

The switch key no longer toggles an overlay. It moves the viewer: the screen shows one instance full-size, and each press transports you to the next instance in the ring, with a short sweep and Doom's own teleport sound, looked up by name in the engine's sound table.

Map 08

One keyboard for three worlds

The switch key misbehaved: a single held press sometimes transported the viewer twice. The cause was another ownership question, and it took a measurement to see it.

Doom 1.9 installs its own keyboard interrupt handler and never passes keys on to the BIOS. Sampled on every frame of a press, the BIOS keyboard buffer never moved. That leaves exactly one channel for input: Doom's own key array, gamekeydown[]. That array is part of Doom's data segment, so it is snapshot state. Each depth has its own copy, and a key event lands in whichever copy happens to be loaded when the interrupt fires.

So the question "is the key down?" has three answers, and each copy only knows about the events that arrived while it was loaded. Below, one press is held across several slices. The top timeline uses the earlier rule, where each depth decides from its own copy and resets its edge tracker at the start of every slice. The bottom timeline uses the current rule.

One press, many copies

Model

The fix moves the answer outside the snapshots. mtx_hs.key_state is a single word in host memory. The root reaches it directly, and a depth reaches it through an address in its parameter block. The rule is the same on both sides:

  1. At the first frame of a slice, force the loaded copy to agree with the authority word. The restored value is what this depth saw last time, and any events since then went to other copies, so the restored value is known to be wrong. Forcing it, instead of clearing a tracker, means a stale "down" is overwritten with the truth instead of turning into a new key press.
  2. On every frame, a key press or release is simply copy != authority. Whoever sees it updates the authority. A different depth can't report the same press, because its copy is either already equal to the authority or gets forced equal at the start of its own slice.

The movement keys hit the same problem in a different form. After being transported into depth 1, the viewer stood still, because the held "forward" key had only ever reached depth 0's copy. The fix has the same shape: mtx_hs.keys is a single 256-byte keyboard state that every depth merges its key events into and adopts at its frame boundary.

Copy less by comparing everything

A naive switch copies the whole registered set twice: about 1.1 MB of memory traffic. A measurement on every switch shows that only about 4,000 of 572,945 bytes (0.6%) actually differ. Most of Doom's data segment is tables that are written once and then only read. That suggests caching which blocks are hot and copying only those. The project tried exactly that, and the widget below lets you watch why it was taken out.

The C loop cost more than two of a depth's own Doom frames per switch. The later range is from the scheduler notes in mtx_boot.c, where a switch still costs more than half a frame. That is why one-frame slices lose.

The live run of the caching version produced 1,000 illegal reads from one wild pointer, and a depth whose frame stopped reaching the screen. By the time the damage was visible, only seven blocks had been promoted to hot. A block can stay cold through the entire warm-up and still be written later, and a canary that checks periodically arrives too late.

The shipped version keeps the hot set for reporting only. Every switch compares every block and copies only the blocks that differ. Correctness then depends on no prediction about what a depth will write, because the comparison itself detects the difference. The commit message describes the result plainly: the same throughput within noise, with about 500 times less emulated memory traffic per switch.

The comparison is the remaining cost, and the instruction used for it matters a great deal inside an emulator. A C loop of compare-and-branch made one switch cost about 6,500 thousand emulated cycles, more than two of the depth's own Doom frames. Replacing it with repe cmpsl, the x86 string instruction that compares until a mismatch, brought it to about 490–1,000 thousand cycles with identical results, verified by a fuzz test of 20,000 random regions. DOSBox runs a string instruction as one tight loop on the host instead of decoding each compare separately.

What the numbers rule out

The handoff notes list the levers that were tested and found not to matter. Raising the emulated CPU speed hit the ceiling. Halving the CPU cap left the frame rate unchanged at 16.00. Patching the PIT timer divisor, skipping the VGA retrace wait, and turning the recorder off all left it unchanged too. Per instance, the frames cost about 2.2 times a vanilla frame, and the ring's bookkeeping explains only a few percent of that. The leading hypothesis, which has not been measured yet, is the per-frame composite: each instance paints another instance's picture into its screen walls every frame.

One measurement detail generalizes to other projects. The figure that matters is how often the picture changes, counted from DOSBox's lossless AVI. The same clip scores 8.47 distinct pictures per second on the AVI and 28.45 on its H.264 re-encode, because compression noise makes "identical" frames differ in their lowest bits.

Map 10

One bug, seven times

Look back over the failures. They seem unrelated: a wild jump, an invalid opcode, a lump name with one letter changed, a key that toggled twice, a level that booted in the wrong slot. Each one has the same cause, which is a piece of state whose owner had been named wrong.

The seventh case is the most recent. A ring boots every level from the root, so the second push happened while the current depth was the root again. cur + 1 named the slot the first child already occupied, and the second level re-booted inside it. The log showed two "depth1 entered" lines with identical addresses and no depth 2 anywhere.

This is the practical lesson of the project. When you multiply a program that was written to be alone, you have to decide, for each piece of state, whether it belongs to the program, to one copy, or to the machine. Then you put it where that owner can reach it and nobody else's restore can overwrite it.

What is not solved

  • Sound. Runs with sound enabled die with NetUpdate: netbuffer->numtics > BACKUPTICS. Inference The likely mechanism is the Sound Blaster's interrupt handler, which runs in whichever depth's context is loaded. Nothing isolates interrupt handlers per depth yet.
  • Containment. A fatal error inside a depth ends the whole program, because the error screen calls dos_exit. One instance should not be able to kill the others, and there is no policy for that yet.
  • Video modes. VESA presents frames through a different path (page flipping), and a nested instance re-running I_InitGraphics is a real mode set that nothing virtualizes.
  • Frame rate. The per-frame composite is the leading suspect and has not been measured. The next step is to time save, load and screen paint per frame in emulated time and compare a frame with the composite turned off.
